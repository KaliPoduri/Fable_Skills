# KB chunk protocol — navigating `etl-knowledge/`

Internal spec: PLAN.md §3 (knowledge-base data model). The KB is a
sharded directory of markdown files generated by `etl-knowledge-builder`
from the org's ETL repos. It is a map, not the territory: chunks hold
navigation, lineage, and narrative with pointers into live code. The
live repo is always the source of truth for code.

## Layout

| File | What it holds |
|---|---|
| `INDEX.md` | Thin root: estate overview, repo table linking per-repo indexes, routing guide. Always read first. |
| `repos/<repo>-index.md` | Per-repo job inventory: job → schedule → entry script → purpose → chunk link; slug↔real-name map. |
| `jobs/<job>.md` | Per job: plain-language flow narrative, entry points, tables/files read and written (each claim with a `repo:path:line` pointer), key params and where they are set, upstream/downstream, known failure points. |
| `lineage/<domain>.md` | Table lineage by data domain/prefix; claims carry pointers. |
| `glossary.md` | Org terms, job families, table naming — newbie language. |
| `errors/index.md` | Error-pattern index: symptom/pattern → dated file + entry. Errors are retrieved by symptom, not date. |
| `errors/<YYYY-MM>.md` | Dated playbook entries: pattern → confirmed cause → fix (schema in references/playbook-entry.md). |
| `meta/generation.md` | Which repos and commit hashes the KB was built from, when, coverage gaps, verification accuracy, build state. |

Job slugs are lowercase alphanumeric with hyphens; the per-repo index
maps slugs to real job names.

## The routing rules

1. **Read the root `INDEX.md` first.** It routes to the right per-repo
   index. Never start anywhere else.
2. **Open at most 3 routed KB files per question.** Typical RCA route:
   `INDEX.md` → `repos/<repo>-index.md` → `jobs/<job>.md`. For an error
   already seen before, check `errors/index.md` by symptom (it may
   replace one hop). If 3 files have not answered the routing question,
   the KB likely lacks coverage — see "When the KB has a gap" below.
3. **Never bulk-read the KB.** No globbing over `jobs/`, no reading
   every lineage file, no loading the whole directory into context. The
   KB is sharded precisely so this is never needed.
4. **Pointers, not copies.** Chunks cite `repo:path:line`. Quote at most
   10 lines of code per excerpt in answers. This cap is a brevity rule,
   NOT a privacy control — privacy is handled by the content-based
   redaction checklist (references/redaction-checklist.md).
5. **Verify in live code before concluding.** Every claim that matters
   to the answer must be checked at its pointer in the LIVE repo. If the
   live code differs from the chunk narrative, the live code wins and
   the answer says the KB is behind.

## Staleness stamps — and their limits

- Every generated chunk records the source commit(s) it was built from
  (`meta/generation.md` holds the per-repo hashes).
- In agent mode, compare the stamp to the live repo before relying on a
  chunk (`git rev-parse HEAD`, or `git log -1 --format=%H -- <path>` for
  a specific cited file). On mismatch: re-verify every pointer used, and
  state the mismatch in the answer.
- Without terminal access (not agent mode), declare it: "staleness
  unchecked — KB may lag the repo." Never present an unchecked chunk as
  current.
- **Stamps cover CODE only.** Runtime scheduler state, deployed configs,
  live schemas and table statistics, and out-of-repo parameters are
  never covered by any stamp. Whenever an answer depends on such a
  value, add at point-of-use: "KB covers code only — verify the live
  value before acting."

## When the KB has a gap

- If the job or repo is missing from the KB, check
  `meta/generation.md` — the gap may be a declared coverage gap.
- Say the gap plainly in the answer, fall back to searching the live
  repo directly (scheduler configs and entry scripts first), and keep
  the same evidence standards.
- Suggest the user run `etl-knowledge-builder` (agent mode) to extend
  the KB; this skill never generates KB chunks itself.
