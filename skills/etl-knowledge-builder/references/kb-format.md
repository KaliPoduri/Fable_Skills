# etl-knowledge — knowledge-base format spec

Distilled from the internal spec PLAN.md §3 (FINAL v5), verified 2026-07-10.
This file is the contract for every file the builder writes. Line budgets
are [CANDIDATE] — they are tuned at the M2 pilot; treat them as targets, not
hard limits, and record any deliberate overshoot in `meta/generation.md`.

## Design rules (apply to every file)

1. **Pointers, not copies.** Chunks hold navigation, lineage, and
   plain-language narrative; the live repo is the code source of truth.
   Code excerpts are at most 10 lines, and every claim carries a
   `repo:path:line` pointer. The 10-line cap is a brevity rule, NOT a
   privacy control — privacy is the content-based redaction checklist
   (`redaction-checklist.md`), which applies to text of any length.
2. **Sharded and chunk-navigable.** Never one huge file. The root index is
   thin; consumers (the etl-assistant skill) read root INDEX → at most ~3
   routed files. Every file must make sense when opened alone.
3. **Newbie contract.** Narratives are plain language for Apache Spark
   newbies; jargon is defined in parentheses at first use (for example
   "partition (a slice of the data processed independently)").
4. **Staleness stamps, code-only scope.** Every generated file's header
   records the source repo commit hashes. Stamps cover CODE ONLY — the
   scope note ships in the header itself (template below) so downstream
   consumers can caveat at point-of-use.
5. **Filename safety.** Job slugs are lowercase alphanumeric plus hyphens;
   numeric suffix on collision (see Slug rules below).
6. **Unverified marking.** A claim whose mechanical cross-check failed is
   written as `[unverified: <reason>]` next to the claim — it never appears
   as plain fact.

## Layout at a glance

| File | Contents | Budget [CANDIDATE] |
|---|---|---|
| `INDEX.md` | THIN root: overview, repo table linking per-repo indexes, routing guide | ~100 lines |
| `repos/<repo>-index.md` | Per-repo job inventory: job → schedule → entry script → purpose → chunk link; slug↔real-name map | ~150 lines each |
| `jobs/<job>.md` | Per job: plain-language flow narrative, entry points, tables/files read & written (each claim with `repo:path:line` pointer), key params and where set, upstream/downstream, known failure points | ~400 lines each |
| `lineage/<domain>.md` | Table lineage by data domain/prefix; split rule on budget overflow; claims carry pointers | ~300 lines each |
| `glossary.md` | Org terms, job families, table naming, newbie language | ~150 lines |
| `errors/index.md` | Symptom-pattern index: symptom/pattern → dated file + entry (errors are retrieved by symptom, not date); split rule on overflow | ~150 lines |
| `errors/<YYYY-MM>.md` | Dated entries: pattern → confirmed cause → fix (schema below) | ~300 lines each |
| `meta/generation.md` | Repos + commit hashes, generated-when, coverage gaps, per-repo accuracy %, build-state checklist, per-job cost log | small |

## File header (every generated file)

Place this at the top of every file the builder writes:

```markdown
<!-- generated by etl-knowledge-builder | generated: YYYY-MM-DD -->
<!-- source commits: <repo>@<short-hash>, <repo>@<short-hash> -->
<!-- Stamps cover CODE ONLY. Runtime scheduler state, deployed configs, and
     live schemas are NOT covered - verify live values before acting. -->
```

The scope note is written INTO the header (not only into `meta/`) so that a
consumer reading a single chunk still sees the caveat and can repeat it at
point-of-use.

## INDEX.md (root, ~100 lines)

Thin root only — never job detail here. Contents, in order:

1. One-paragraph overview: what the KB is, what it is generated from, that
   the live repos are the source of truth.
2. Repo table: `| Repo | Purpose | Jobs | Index |` — one row per repo,
   linking `repos/<repo>-index.md`.
3. Routing guide — where a consumer goes for each question type:
   - "Job failed / error message" → `errors/index.md` (by symptom), then
     the job's chunk.
   - "How does job/flow X work" → per-repo index → `jobs/<job>.md`.
   - "Where does table T come from / go to" → `lineage/<domain>.md`.
   - "What does this term mean" → `glossary.md`.
   - "How fresh is this KB / what is missing" → `meta/generation.md`.
4. Link to `meta/generation.md`.

Written LAST in every build so it never links to a file that does not exist.

## repos/<repo>-index.md (~150 lines each)

1. Repo purpose, one short paragraph.
2. Job inventory table — one row per job:
   `| Job (slug link) | Schedule | Entry script | Purpose |`
   Schedule as stated in the scheduler artifact or seed; entry script as a
   repo-relative path.
3. Slug↔real-name map: `| Slug | Real job name |` — real names may contain
   characters that are unsafe in filenames; the map is the lookup bridge.
4. Inventory provenance line: which seed this inventory was confirmed
   against, and — when the list was built interactively —
   `inventory: human-confirmed <date> by <who>`.

## jobs/<job>.md (~400 lines each)

Section order is fixed:

```markdown
# <real job name> (`<slug>`)

## What this job does
<1–3 plain-language paragraphs: what comes in, what happens, what goes
out, when it runs. Spark-newbie language; jargon defined in parentheses.>

## Entry points
- <repo:path> — <how it is invoked (scheduler artifact, wrapper script)>

## Reads
| Table / file | Confirmed at | Notes |
|---|---|---|
| <name> | <repo:path:line> | <or [unverified: reason]> |

## Writes
| Table / file | Confirmed at | Notes |
|---|---|---|

## Key parameters
| Parameter | Set where | Pointer |
|---|---|---|
<parameter NAMES and where the value is set; values only when they are not
data values — see redaction-checklist.md. Runtime-injected values: say so;
that is a code-only stamp limit, not a gap to guess.>

## Upstream / downstream
- Upstream: <job> — <why (scheduler dependency | writes a table this job
  reads [inferred])>
- Downstream: <job> — <why>

## Known failure points
<only what the code shows (retries, error handling, fragile paths, TODOs)
or the user has stated; never invented. Link errors/ entries if any.>
```

Excerpts (≤10 lines) may appear where they genuinely help; each must sit
under a pointer to its source.

## lineage/<domain>.md (~300 lines each)

Grouped by data domain or table-name prefix (for example `billing`,
`stg_`). Per table:

```markdown
## <table name>
- Produced by: <job slug> — <repo:path:line> <or [unverified: reason]>
- Consumed by: <job slug> — <repo:path:line>; <job slug> — ...
- Notes: <format, partitioning, retention — only if stated in code>
```

**Split rule:** when a domain file would exceed its budget, split by
sub-domain or prefix (`lineage/billing-invoices.md`), then update every
link to it (per-repo indexes and root INDEX).

## glossary.md (~150 lines)

Org terms, job-family names, table naming conventions, and newbie
definitions of recurring technical terms. Initialized by the builder from
what the repos show; thereafter human-curated — on regeneration, append new
terms and NEVER delete or rewrite existing entries.

## errors/index.md (~150 lines)

Symptom-pattern index so errors are found by symptom, never by date:

```markdown
| Symptom / error pattern | Job(s) | Entry |
|---|---|---|
| <e.g. "container killed by YARN — memory overhead"> | <slug> | errors/2026-06.md#<anchor> |
```

Same split rule as lineage files on budget overflow.

## errors/<YYYY-MM>.md (~300 lines each)

Dated playbook entries. Entry schema (fixed — internal spec §5):

```markdown
## <anchor: slug-of-symptom>
- Date: YYYY-MM-DD
- Job: <slug>
- Symptom / error pattern: <what the user saw>
- Confirmed cause: <user-confirmed root cause>
- Fix: <what resolved it>
- Verification evidence: <how the fix was proven>
- Redaction-check done: yes
```

Entries are normally drafted by the etl-assistant skill after a
user-confirmed root cause and land via PR under the org's playbook
governance. The builder creates the `errors/` structure and, on
regeneration, preserves existing entries byte-for-byte — they are
human-curated, not derived from code.

## meta/generation.md (small)

```markdown
# Generation record

## Repos and commits
| Repo | Commit | Generated |
|---|---|---|

## Coverage gaps
- <job/artifact>: <what is missing and why>

## Per-repo accuracy
| Repo | Cross-checks run | Passed | Accuracy % |
|---|---|---|---|

## Build state — <build id, e.g. full-2026-07-10>
- [ ] seed confirmed (<source>)
- [ ] inventory confirmed with user
- Repo <name> @ <hash>
  - [ ] <job slug>: traced, cross-checked, written, redacted
  - [ ] lineage updated
  - [ ] repos/<name>-index.md written
- [ ] root INDEX.md rewritten (LAST)
- [ ] stamps + meta finalized

## Per-job cost log
| Job | Prompts | ~Tokens | Wall time | Date |
|---|---|---|---|---|
```

Updated after EVERY job (tick + cost row), not at the end — this is what
makes builds resumable. Keep a build-state block per build; old blocks stay
as history.

## Slug rules (filename safety)

1. Lowercase the real job name.
2. Replace every run of characters outside `a-z0-9` with a single hyphen.
3. Trim leading/trailing hyphens.
4. On collision within the KB, append `-2`, `-3`, ... in discovery order.
5. Record the slug↔real-name pair in the per-repo index map.

Example: `Billing/DAILY Rollup (v2)` → `billing-daily-rollup-v2`.

## Budget overflow handling

Budgets are [CANDIDATE] until tuned at M2. On overflow: for `lineage/` and
`errors/index.md`, apply the split rules above. For `jobs/` chunks, first
trim narrative and excerpts; a job chunk that still cannot fit ~400 lines
is usually several jobs sharing one entry point — re-check the seed rather
than splitting the chunk.
